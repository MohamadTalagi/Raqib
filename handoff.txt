2. THE REQUEST, AND THE REASONING BEHIND THE CHOSEN APPROACH
================================================================================
The owner's own words: "currently users are expected to upload their own
firmware for CVE assessment. This is kinda counter intuitive and most
auditors wont have a firmware file on-hand, can we make it such that it gets
the firmware and vendors from fingerprinting and it does web-based firmware
grabbing to fill the database on whether theres CVE vulnerabilities in the
firmware version or if its out of date. Would you recommend this solution."

**Why the literal "web-based firmware grabbing" idea was rejected, not
built as asked:**
1. No uniform source exists. There is no index of "vendor X, model Y,
   firmware Z -> download URL." Real commercial tools that do this
   (Finite State, ONEKEY, Eclypsium) rely on licensed firmware corpora and
   direct vendor relationships built over years — not live scraping per
   assessment. A DIY scraper would be a vendor-by-vendor, portal-by-portal
   maintenance burden (login walls, CAPTCHAs, ToS) that breaks constantly.
2. Real legal/ToS risk in auto-downloading and redistributing real vendor
   firmware binaries programmatically — a different risk profile than
   anything else this project has taken on.
3. **It would not even be meaningful for THIS lab specifically.** This
   project's device fixtures (lab/devices/*) are small FastAPI apps with
   hardcoded fake version strings — not the real vendor's actual embedded
   Linux firmware image. The vendor identities (Hikvision, Axis, Yale,
   Schneider Electric, Netgear, Dahua, Sonos — see the 2026-08-04
   "device-vendor-realism" changelog entry in CLAUDE.md) were deliberately
   scoped to protocol-banner/CVE-citation realism only, NOT a full firmware
   rewrite. Downloading and Grype-scanning the REAL Hikvision/Netgear/etc.
   firmware would produce CVE results for code that isn't actually running
   in this lab at all — worse than the current honest "no data" state,
   because it would look authoritative while being disconnected from
   reality.
4. There's also a prerequisite gap that would block the literal approach
   even if it were otherwise a good idea: **vendor/model are currently
   100% self-reported** (a human types them in at device registration or
   via PATCH) — there is no automated collector today that fingerprints a
   device's vendor/model/firmware-version into structured fields at all.
   "Auto-detect vendor+model from fingerprinting" isn't fully built yet
   either way, so it had to be designed from scratch regardless of which
   downstream approach was chosen.

**What was recommended and agreed with the owner instead:** skip the binary
entirely. Match the device's vendor + model + firmware-version (learned
automatically via a new fingerprinting collector, not typed in by a human)
against a **real CVE database (NVD)**, the same technique Shodan/Vulners/
cve-search use — CPE-based version matching, no firmware image needed at
all. This is strictly better for the platform's actual audience (an
auditor who has never seen the device's firmware file, only its network
presence) and it closes a limitation `docs/vulnerability-intelligence.md`
ALREADY names explicitly as scoped-out: *"Package/component-level only —
device-level vendor/model CPE matching... is not implemented... explicitly
scoped out of this pass."* This is not scope creep; it's finishing a
already-planned-for gap.

**A genuinely nice side effect discovered during design, not planned for
up front:** `policies/controls/SA-IOT-001.yaml` (control: "Device
identification and asset inventory") has referenced a test_id called
`TEST-DEVICE-ID` since Day 3 of this project — but that test_id has **never
had a `SCAN_CATALOG` collector implemented**, confirmed absent by
repo-wide grep and independently corroborated by `docs/known-limitations.md`
and a comment in `lab/auditor/api/main.py:1201-1205`. SA-IOT-001 has
therefore been "never automatically evaluated in practice" for the entire
life of this project. Implementing the identity-auto-detection collector
(Part 1 below) finally builds this exact test_id, closing a long-standing,
independently-documented gap as a side effect of solving the owner's actual
request — not a coincidence to be surprised by, a deliberate reuse.

## 5.1 Device identity today — 100% self-reported, no automated collector

- `devices.vendor`/`devices.model` columns exist
  (lab/auditor/db/init.sql:147-171) but are written ONLY by a human, via
  `POST /devices` (lab/auditor/api/main.py:1421-1481,
  `_validate_device_payload` at :1381-1382) or `PATCH /devices/{id}`
  (:1735-1778, `PATCHABLE_DEVICE_FIELDS` at :1546-1550 includes
  "vendor","model"). Confirmed by grepping the ENTIRE worker/api tree for
  `UPDATE devices` — the only other writes touch firmware_filename/sha256/
  uploaded_at (upload metadata for an uploaded archive), never vendor/model.
- There is **no `devices.firmware_version` column today** — only
  `firmware_filename`/`firmware_sha256`/`firmware_uploaded_at` (upload
  metadata, not a self-reported version string). This plan adds
  `firmware_version` as a new column.
- `TEST-DEVICE-ID` is referenced in `policies/controls/SA-IOT-001.yaml:11-12`
  (`automated_test_ids: [TEST-DEVICE-ID]`) but has **no `SCAN_CATALOG`
  entry anywhere** — confirmed absent by repo-wide grep, corroborated by
  `docs/known-limitations.md:207-211` and `main.py:1201-1205`'s own comment
  ("Only some required tests have an automated collector... If none do
  (e.g. SA-IOT-001's TEST-DEVICE-ID)...").
- **SA-IOT-001.yaml's exact contract (read directly, full file):**
  ```yaml
  control_id: SA-IOT-001
  title: Device identification and asset inventory
  version: "1.0.0"
  saudi_source:
    - framework: CGIoT-1:2024
      reference: "2-1-1"
      clause: "Maintain an accurate inventory of connected IoT devices, including vendor, model, and identifiers."
  applicability:
    device_type: [smart-camera]      # <-- CONFIRMED INERT, see below
  required_evidence:
    - test_id: TEST-DEVICE-ID
  automated_test_ids: [TEST-DEVICE-ID]
  severity: medium
  conditions:
    pass: { field: "observations.device_identified", op: "equals", value: true }
    fail: { field: "observations.device_identified", op: "equals", value: false }
    partial: null
    inconclusive: { when: "evidence_missing_or_low_confidence" }
  remediation: "Expose vendor, model, MAC, and firmware version via an unauthenticated read-only device-info endpoint for asset inventory tooling."
  limitations: "Only checks whether a device-info endpoint discloses vendor/model/firmware; does not verify the values are accurate, does not check MAC address disclosure, and does not cover devices with no HTTP service at all (evaluates to NOT_APPLICABLE for those)."
  ```
  The new collector's `observations` dict MUST use the exact key name
  `device_identified` (boolean) — this is a hard, pre-existing contract,
  not a naming choice to make freely. Per the control's own `limitations`
  text, MAC disclosure is explicitly NOT part of the pass condition — only
  vendor+model+firmware_version need to be present for `device_identified`
  to be true.
- `applicability.device_type: [smart-camera]` in the YAML above is
  **confirmed inert** — this codebase's `policy_engine.py`/`is_applicable()`
  never reads that field at all (a fact already established and documented
  in multiple past CLAUDE.md sessions: "never the unused
  applicability.device_type YAML field, which corresponds to no column
  devices actually have"). Real applicability comes from
  `applicable_service_types` matching a device's registered
  `device_services` rows. This means implementing TEST-DEVICE-ID correctly
  makes SA-IOT-001 evaluable for EVERY device with an HTTP/HTTPS service,
  not just smart-camera-derived ones, despite what the YAML's stale
  `device_type` field suggests.

## 5.3 Pipeline/catalog architecture (policies/catalog/scan_tests.py)

- `SCAN_CATALOG` dict; each entry has `build_command`, `parse_observations`,
  `applicable_service_types`, `pipeline_phase`, `category`, `tool`,
  `tool_version_command`, optional `timeout_seconds`.
- `pipeline_phase` constants (`:86-93`): `PIPELINE_PHASE_FINGERPRINTING`,
  `PIPELINE_PHASE_SA_IOT_COMPLIANCE`, `PIPELINE_PHASE_VULN_INTELLIGENCE`,
  `PIPELINE_PHASE_PQC_READINESS`.
- `TEST-FW-MANIFEST` (`:1984-1994`, pipeline_phase=VULN_INTELLIGENCE) has
  `applicable_service_types: ()` — no live host/port needed, only
  `device_id`. This is the exact pattern the new `TEST-DEVICE-CVE-LOOKUP`
  test must copy.
- **`is_firmware_test()` — read directly, confirmed exact implementation:**
  ```python
  def is_firmware_test(test_id: str) -> bool:
      spec = SCAN_CATALOG.get(test_id)
      return spec is not None and spec["category"] == CATEGORY_FIRMWARE

  def is_network_discovery_test(test_id: str) -> bool:
      """True for tests that sweep the whole audit-network subnet rather than
      a registered device's host/port - like firmware tests, these carry
      applicable_service_types=() and skip live-target validation entirely
      (see resolve_target() in job_runner.py and _create_scan_job() in
      main.py)."""
      spec = SCAN_CATALOG.get(test_id)
      return spec is not None and spec["category"] == CATEGORY_NETWORK_DISCOVERY
  ```
  This is a plain category check. **The cleanest way to give
  `TEST-DEVICE-CVE-LOOKUP` the same no-live-target treatment as
  `TEST-FW-MANIFEST` is to assign it `category = CATEGORY_FIRMWARE` too** —
  zero changes needed to `is_firmware_test()`, `job_runner.py`'s dispatch,
  or `main.py`'s scan-job creation logic. (This also means it will appear
  in the dashboard's "Simulated Firmware Analysis" Run-Scan section
  alongside TEST-FW-MANIFEST — which reads fine given its label "Device CVE
  lookup (NVD, no firmware required)" makes the distinction obvious inline.)
- Fingerprinting-phase tests today (7): TEST-NET-REACHABILITY,
  TEST-NET-PORTSCAN, TEST-MODBUS-PROBE, TEST-RTSP-PROBE, TEST-UPNP-PROBE,
  TEST-MDNS-PROBE, TEST-NET-HTTP-INSPECT. None produce clean structured
  vendor/model/firmware fields today (confirmed — raw banners only; nmap
  version text is explicitly commented in the source as unreliable to
  auto-match against a small reference table). `TEST-DEVICE-ID` becomes an
  8th.

- `lab/auditor/worker/job_runner.py`:
  - Constants block (:71-87): per refresher, a

    `*_REFRESH_SENTINEL` (a touch-file path, distinct from the cache file
    itself — its mtime alone is the staleness signal).
  - `maybe_refresh_cisa_kev()` (:455-478) is the exact template: in-process
    gate -> sentinel-age gate -> fetch -> touch sentinel only on success.
    `maybe_refresh_grype_db`/`maybe_refresh_oui_registry` are structurally

  - `main()`'s poll loop (:586-597) calls all of
    `maybe_refresh_network_scope()`, `poll_once()`,
    `poll_network_scans_once()`, `poll_automated_runs_once()`, then
    `maybe_refresh_grype_db()`, `maybe_refresh_cisa_kev()`,
    `maybe_refresh_oui_registry()`, all wrapped in **one blanket
    try/except** so a refresh failure never kills the poll loop. **A new
    `maybe_refresh_device_cve_index()` must be added to this exact list.**
- **Networking, confirmed from docker-compose.yml**: `auditor-worker` sits
  on BOTH `audit-network` (non-internal — real outbound internet via Docker
  NAT) and `internal-network`. `auditor-api` sits ONLY on `internal-network`

  docstring says the API "has no access" to Grype/KEV data and only ever

  new outbound fetch (to NVD) must happen from the worker container, never
  from auditor-api.**

## 5.5 How package-level CVE merging works today (the pattern to mirror at
    the device level)

- The merge happens at **write time**, inside
  `policies/catalog/scan_tests.py`'s `_parse_fw_manifest_observations`
  (:1587-1635) — NOT at read time. 3-tier fallback per package: (1) a real
  Grype match if present, (2) the static `vuln_reference.py` table if it
  has real data, (3) an honest "no data" shape — **never fabricated**.
- `lab/auditor/api/vuln_routes.py` is **purely read-only**: it re-reads the
  already-merged `evidence.observations` JSONB
  (`SELECT DISTINCT ON (device_id) ... FROM evidence WHERE test_id =
  'TEST-FW-MANIFEST' ORDER BY device_id, timestamp DESC`) and does only
  light Python-side aggregation. **Zero CVE/KEV lookup logic lives in this
  file** — it already happened when the evidence was written. The new
  device-level CVE feature must follow this exact split: real lookup logic
  lives in the worker (write time); the API stays a dumb, honest read of
  whatever the worker already recorded.
- `evidence` has no FK to `devices` (deliberate — evidence must outlive
  deregistration). `record_scan_job_evidence`
  (`lab/auditor/api/main.py:802-867`) is the ONE function that turns a
  completed `scan_jobs` row + a human-typed finding into a real `evidence`
  row — this is the only existing hook point for "something happens after
  evidence is recorded." Nothing writes back to `devices` from it today —
  that's new in this plan (Part 1).
- Existing types to mirror, `lab/auditor/web/src/lib/types.ts:707-728`:
  `VulnCVE {id, cvss, summary, kev_listed, kev_date_added}`,
  `VulnPackageAdvisory {name, version, outdated, eol, latest_known_version,
  official_patch_available, patched_version, kev_listed_count, cves, notes}`.
- `policies/catalog/sbom.py`'s `CPE_OVERRIDES: dict[str, str]` (:20-22,
  maps lowercased package name -> "vendor:product") is the exact precedent
  for a small, hand-verified override table where naive name-lowercasing
  doesn't match a real CPE vendor:product string. Mirror this exactly for
  device vendor/model -> real NVD CPE vendor:product strings (§6, Part 2).
- `policies/catalog/vuln_reference.py`: static (name,version)-keyed offline
  fallback, 6 entries, `ComponentAdvisory`/`CVE` dataclasses,
  `lookup_component()` always returns the same dict shape whether it hits
  or misses (never partially fabricated) — same "small, bounded,
  honest-miss" discipline to follow for any new lookup/override table here.

  `job["test_id"] == "TEST-DEVICE-ID"` and the recorded evidence's
  `observations.device_identified` is `true`. If so:
  1. `SELECT vendor, model, firmware_version FROM devices WHERE device_id
     = %s FOR UPDATE` (row lock to avoid a race with a concurrent PATCH).
  2. In Python, compute which of `vendor`/`model`/`firmware_version` are
     currently `NULL` on that row.
  3. If at least one is `NULL`, `UPDATE devices SET
     vendor = COALESCE(vendor, %s), model = COALESCE(model, %s),
     firmware_version = COALESCE(firmware_version, %s),
     identity_source = 'auto_detected' WHERE device_id = %s` — **but only

     regression test proving a manually-set `vendor` survives a
     `TEST-DEVICE-ID` evidence recording untouched.

def maybe_refresh_device_cve_index(now: float | None = None) -> None:
    """Same hybrid model/sentinel pattern as maybe_refresh_cisa_kev, for
    the NVD device-CVE cache (nvd_lookup.py). Only queries NVD for
    (vendor, product) pairs actually present in the registered fleet right

        _last_nvd_cve_check_monotonic is not None

        return

    if sentinel_age is not None and sentinel_age < NVD_CVE_MAX_AGE_SECONDS:
        return

        response.raise_for_status()

        print(f"job_runner: device CVE index refresh failed (could not list devices): {exc}", file=sys.stderr, flush=True)
        return

    pairs = {

        for d in devices
        if d.get("vendor") and d.get("model") and (d["vendor"], d["model"]) in DEVICE_CPE_OVERRIDES

    if nvd_lookup.fetch_and_cache_device_advisories(list(pairs)):
