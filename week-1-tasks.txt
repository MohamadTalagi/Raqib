Week 1
Build a stable first version of the IoT Compliance Auditor that automatically assesses the three simulated device profiles using the first five controls.
Tasks
1. Complete the assessment workflow
Implement the complete flow:
Select device
→ create assessment
→ run collectors
→ generate structured evidence
→ evaluate policies
→ store verdicts
→ display results
→ export report
The system must support:
•	Insecure device 
•	Partially hardened device 
•	Hardened device 

2. Complete device and assessment management
Try and Implement:
•	Device registration and selection 
•	Assessment creation 
•	Assessment status tracking 
•	Assessment history 
•	Error reporting 
•	Assessment cancellation or timeout handling 
Required assessment statuses (could be):
•	Queued 
•	Running 
•	Partially completed 
•	Completed 
•	Failed 
•	Cancelled 
Store:
•	Device ID 
•	Assessment ID 
•	Start and completion time 
•	Policy version 
•	Collector versions 
•	Assessment status 
•	Errors 
•	Evidence references 
•	Verdict references 

3. Build the automated network collector
Automatically test:
•	Host reachability 
•	Open TCP ports 
•	Service identification 
•	HTTP availability 
•	HTTPS availability 
•	Telnet exposure 
•	MQTT exposure 
•	MQTT authentication 
•	MQTT encryption 
•	TLS certificate presence 
•	TLS certificate validity 
•	Supported TLS versions 
The collector must:
•	Use target allow-listing 
•	Use fixed commands 
•	Apply timeouts 
•	Capture tool versions 
•	Preserve stdout and stderr 
•	Store raw artefacts 
•	Hash raw artefacts using SHA-256 
•	Handle collector failures correctly 
A failed collector should produce Inconclusive, not automatically Fail.

4. Finalise the structured evidence model
Every evidence record must include:
•	Evidence ID 
•	Assessment ID 
•	Device ID 
•	Test ID 
•	Source type 
•	Tool 
•	Tool version 
•	Typed observed value 
•	Timestamp 
•	Confidence 
•	Confidence reason 
•	Raw artefact path 
•	Raw artefact hash 
•	Error state 

5. Complete the first five controls
Implement:
1.	Device identification 
2.	Default credentials 
3.	Open and unnecessary services 
4.	Insecure protocols 
5.	TLS and certificate configuration 
Each policy must support:
•	Applicability 
•	Required evidence 
•	Pass 
•	Fail 
•	Partial 
•	Inconclusive 
•	Not Applicable 
•	Severity 
•	Confidence 
•	Saudi source mapping 
•	Remediation 
•	Limitations 
The policy engine must evaluate structured values, not prose.

6. Add evidence conflict handling
The system must handle conflicting evidence.
Example:
•	Documentation claims MQTT uses TLS. 
•	Packet capture shows plaintext MQTT. 
The system must:
•	Record both evidence items 
•	Prefer directly observed technical evidence 
•	Mark the conflict 
•	Explain the resulting verdict 

7. Complete storage
Use PostgreSQL if the current implementation is stable. SQLite is acceptable only if needed for simplicity.
Store:
•	Devices 
•	Assessments 
•	Collector runs 
•	Evidence metadata 
•	Verdicts 
•	Policy versions 
•	Report records 
•	Audit events 
•	Manual evidence decisions 
The system must retain previous assessments after restart.

8. Complete the web interface
The interface must allow the user to:
•	Select or register a device 
•	Start an assessment 
•	View progress 
•	View collector errors 
•	View verdicts 
•	View severity and confidence 
•	View Saudi source mapping 
•	View evidence provenance 
•	Open raw artefact references 
•	View remediation 
•	Export the report 
Visual polish is not the priority.

9. Generate reports
Generate:
•	HTML report 
•	JSON report 
The report must include:
•	Device profile 
•	Assessment scope 
•	Assessment methodology 
•	Policy version 
•	Tool versions 
•	Control results 
•	Evidence references 
•	Confidence 
•	Severity 
•	Saudi mapping 
•	Conflicting evidence 
•	Controls not assessed 
•	Remediation 
•	Limitations 
•	Disclaimer that the report is not official certification 

10. Test the complete system
Minimum tests:
•	Four tests per control 
•	Pass case 
•	Fail case 
•	Inconclusive or missing-evidence case 
•	Contradictory-evidence case 
•	Parser tests for all three device profiles 
•	API workflow tests 
•	Database persistence test 
•	Collector timeout test 
•	Malformed evidence test 
•	Command-injection prevention test 
•	One complete assessment test per device profile 
•	Clean deployment smoke test 
By the end of Week 1
You should try to have completed (at least):
•	A working end-to-end auditor 
•	Three assessable Docker device profiles 
•	Five working controls 
•	Automated network evidence collection 
•	Structured evidence storage 
•	Persistent database 
•	Functional web interface 
•	HTML and JSON reporting 
•	Automated tests 
•	Updated architecture diagram 
•	Updated README 
•	Known limitations register 
Week 1 completion demonstration
You should demonstrate:
1.	Start the full platform on a clean deployment. 
2.	Assess the insecure device. 
3.	Show collected evidence. 
4.	Show five verdicts. 
5.	Trace one verdict back to its policy rule and raw artefact. 
6.	Export the report. 
7.	Repeat the assessment for the hardened device. 
8.	Explain the different results. 
9.	Show handling of one collector failure. 
10.	Show passing tests.
