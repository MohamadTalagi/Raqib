# Per-Device PDF Compliance Report — Design Spec

**Date:** 2026-07-19
**Status:** Approved
**Depends on:** the device-registration feature (`worktree-device-registration`) being merged to `main` first.

Adds a downloadable, print-quality PDF assessment report for a single device, generated
server-side from the database and the NCA control definitions.

---

## 1. Scope decisions

Settled during brainstorming:

1. **Per-device report**, generated from the device detail page — not a whole-lab or
   per-control report. Those may follow later if they earn their keep.
2. **IoTGuard branding with an NCA citation.** The report carries the IoTGuard mark and the
   line "Assessed against NCA CGIoT-1:2024", plus per-control `§` references and clause text.
   It does **not** carry the NCA emblem — see §2.
3. **Full provenance table, no raw-output appendix.** Each evidence record contributes tool,
   tool version, exact command, timestamp, confidence and SHA-256. The raw tool output itself
   is cited by path and hash, not embedded.
4. **Server-side generation with WeasyPrint** (`GET /devices/{id}/report.pdf`), chosen over
   client-side `@react-pdf/renderer` and a print stylesheet.
5. **Implementation waits until `worktree-device-registration` is merged.**

## 2. Branding constraint (deliberate, do not "fix" later)

NCA is Saudi Arabia's national cybersecurity regulator. A generated document that states
pass/fail verdicts and carries NCA's official emblem reads as an assessment *issued by NCA*
rather than one this tool produced against NCA's published guidelines.

The report therefore uses **IoTGuard's own branding** and states the relationship in words:
"Assessed against NCA CGIoT-1:2024", with each control's `framework §reference` and its clause
text quoted verbatim from the control YAML. This is accurate and implies no endorsement.

No NCA emblem is to be added without the owner confirming rights and supplying the real asset.

## 3. Report structure

Six blocks, in order. Every value is a fixed label, a database value, or text copied verbatim
from a control YAML. **No LLM-generated narrative anywhere** — a generated executive paragraph
would undercut the project's "AI-assisted, not AI-decided" determinism rule.

**Title block** — IoTGuard mark; "Device Security Assessment"; device display name and
`device_id` (mono); tier badge; generation timestamp; "Assessed against NCA CGIoT-1:2024".

**1. Device profile** — `device_id`, host, description; inventory fields (vendor, model,
location, owner, notes); `source` (`seeded` / `manual`); registration timestamp.
Unset inventory fields render as **"Not recorded"**, never blank, so *absent* is
distinguishable from *not collected*.

**2. Exposed services** — table of service type, internal port, published port, enabled, with
a one-line explanation of the internal-vs-published distinction (the value a reader is most
likely to misread). A null `published_port` renders as **"not browser-reachable"**.

**3. Compliance summary** — one row per control assessed against this device: control ID,
title, severity, `CGIoT-1:2024 §x-y-z`, verdict status, plus totals. The skim page.

**4. Findings** — per control with a verdict: the clause text verbatim from
`saudi_source.clause`; the verdict; **the exact condition that produced it** (e.g.
`observations.default_creds equals True`); and the remediation from the control YAML. The
condition line is what makes a verdict auditable rather than asserted.

**5. Evidence provenance** — `evidence_id`, `test_id`, tool, tool version, exact command,
timestamp, confidence, SHA-256. This is the reproducibility claim made concrete: a reader can
re-run the command and check the hash.

**Page furniture** — running header (device name, report title); footer ("Generated by
IoTGuard", generation timestamp, `page N of M`).

## 4. Architecture

### New files

| File | Responsibility |
|---|---|
| `lab/auditor/api/report.py` | Builds the report data model; orchestrates rendering |
| `lab/auditor/api/templates/device_report.html` | Jinja2 template — structure only |
| `lab/auditor/api/templates/report.css` | Paged-media stylesheet — all layout and typography |
| `lab/auditor/api/assets/fonts/` | Vendored Inter Regular, Inter SemiBold, JetBrains Mono Regular (see font-format note in §4) |

`main.py` gains exactly one route: `GET /devices/{device_id}/report.pdf`. Adding a focused new
module is consistent with the owner's "keep `main.py` a single file" decision, which concerned
not relocating existing routes.

### The pure/render split

`build_report_model(conn, device_id) -> dict` is a **pure data function**: it reads device,
services, evidence and verdicts, joins in control metadata from the YAML files, and returns a
plain dict. Rendering is separate.

Consequence: almost every test runs without WeasyPrint installed, and report *content* can be
asserted directly (does the provenance table carry the right hash? does a failing control pull
the right clause?) without parsing a PDF.

### Flow

1. Validate `device_id` via `device_validation.validate_device_id` — the same guard every other
   device route uses
2. 404 if the device is unknown
3. `build_report_model(...)`
4. Jinja2 renders HTML
5. WeasyPrint renders HTML + CSS to PDF bytes
6. Return `application/pdf` with
   `Content-Disposition: attachment; filename="iotguard-<device_id>-<YYYY-MM-DD>.pdf"`

The filename is safe to interpolate because `device_id` is constrained to
`^[a-z0-9][a-z0-9-]{0,62}$` — no quotes, slashes or newlines can reach the header. Header
injection is the obvious risk in a download endpoint; this is why it does not apply.

### Accepted costs

- **Container weight.** WeasyPrint needs pango, cairo and gdk-pixbuf. The `auditor-api`
  Dockerfile gains an `apt-get` layer, realistically 100-150 MB. This is the price of
  server-side rendering and it is not small.
- **Vendored fonts (~1 MB committed).** The design system's Inter and JetBrains Mono live in the
  web app's `node_modules` via `@fontsource`; the API container cannot see them. The three
  required faces are vendored into the repo and referenced via `@font-face`. The alternative —
  base-image fallback fonts — would make the PDF look unrelated to the dashboard.

  **Font-format note (resolve at implementation, do not assume):** `@fontsource` ships
  **`.woff` / `.woff2` only — no `.ttf`**, so the files cannot simply be copied from
  `node_modules` as an earlier draft of this spec implied. WeasyPrint resolves fonts through
  fontconfig/pango, where TTF/OTF is the most reliable format and `woff2` support varies by
  version. The first implementation step is therefore to confirm what the pinned WeasyPrint
  version actually accepts, and source the faces accordingly — either the upstream Inter and
  JetBrains Mono TTF releases, or the `@fontsource` `woff2` files if verified working. Do not
  proceed on the assumption that either format works; render a page containing `§`, `—` and a
  SHA-256 string and confirm the glyphs appear.

### Frontend

A "Download report" button on `DeviceDetailPage` linking directly to the endpoint. No
client-side generation, no new frontend dependency.

## 5. Visual design

**The report is a light document, not a dark one.** The dashboard's near-black theme is correct
on screen and wrong on paper — it burns ink and reads badly in a document reader. Brand identity
carries through typography, the amber accent and the severity colour language instead.

- **Page:** A4, 18 mm margins.
- **Type:** Inter for prose, JetBrains Mono for every machine value (`device_id`, hosts, ports,
  commands, hashes, control IDs). The split tells a reader at a glance which strings are literal
  and reproducible. ~16 pt title, 11 pt section headings, 9 pt body, 8 pt tables.
- **Colour:** near-black text on white; muted grey field labels; amber rules and mark. Verdict
  and severity colours keep the dashboard's language but darkened for contrast on white (the
  dashboard's `#4ADE80` green is unreadable on paper).
- **Status is never colour alone.** `PASS` / `FAIL` / `PARTIAL` / `INCONCLUSIVE` always render as
  the word, with colour as reinforcement. The report will be printed in greyscale and read by
  colourblind people; a compliance verdict is the wrong thing to encode in hue alone.
- **Tables:** hairline rules and generous row padding, not zebra striping. The provenance table
  is the dense one — 8 pt mono with `overflow-wrap` so a long command wraps instead of
  overflowing, and the 64-character SHA-256 wraps rather than shrinking to unreadability.
- **Page-break control:** `break-inside: avoid` on each finding block so a control's clause,
  verdict and remediation never split across pages; `break-after: avoid` on headings so none is
  orphaned at a page bottom. Getting this wrong is the most common reason generated PDFs look
  amateur.
- **No emojis**, consistent with the rest of the project.

## 6. Error handling and edge cases

| Case | Behavior |
|---|---|
| Unknown device | 404 |
| Malformed `device_id` | 400 `{field, detail}` via the existing global `ValidationError` handler |
| Device with no evidence (e.g. `telnet-sim`) | Structurally complete report with explicit "No evidence recorded for this device" — a broken-looking report and a correct empty one must be distinguishable |
| Verdict whose control YAML is missing | Verdict still renders from stored data (`control_id`, status, severity, reason); clause and remediation marked unavailable |
| Renderer failure (missing libs/fonts) | 500, error logged; never a truncated or corrupt PDF |
| Long commands / notes / hashes | CSS wrapping (§5) |
| Non-ASCII | UTF-8 end to end; vendored fonts must carry `§` and `—` |

**On the missing-control-YAML case:** verdicts are database rows and controls are files on disk,
so they can drift. Dropping a verdict whose control file vanished would silently remove a FAIL
from a compliance document — the dangerous failure. It is rendered incomplete instead.

**On non-ASCII:** this is a live case, not hypothetical. The data already contains `§` in NCA
references and em-dashes in display names ("Smart Camera — Insecure"). Glyph coverage is to be
verified in rendered output, not assumed — a missing glyph renders as a blank box in exactly the
place a reader looks.

## 7. Testing

**Model tests (no WeasyPrint required):**
- correct structure for a device with evidence, and for one without
- control metadata joined correctly onto verdicts
- a verdict with a missing control YAML still appears, marked incomplete
- **provenance fidelity:** every evidence record's `command`, `tool_version` and `sha256` reach
  the model byte-identical. This is the reproducibility claim, so it gets its own assertion
  rather than being assumed.

**Route tests:** 404 unknown device; 400 malformed ID; 200 returning `application/pdf` with the
correct `Content-Disposition`.

**Render smoke test:** one test asserting output starts with `%PDF-` and is non-trivially sized.
Skipped when WeasyPrint is unavailable locally, following the same skip pattern the seed tests
use for an absent database.

**Visual verification:** render a real PDF from real PC data and put it in front of the owner for
sign-off before this is called done. Passing tests said nothing about whether the Flutter
dashboard looked right; the same applies here.

## Decisions log

| Decision | Chosen | Rejected alternatives |
|---|---|---|
| Branding | **IoTGuard + NCA citation** | NCA emblem (implies issuance by the regulator); explicit unofficial-notice footer |
| Report scope | **Per-device** | Whole-lab assessment; per-control; full-then-others |
| Evidence depth | **Full provenance table** | Provenance + raw output appendix; findings only |
| Generation | **Server-side WeasyPrint** | `@react-pdf/renderer` (browser-only, no headless generation); print stylesheet (no page control) |
| Document theme | **Light** | Matching the dashboard's dark theme (burns ink, reads badly on paper) |
| Sequencing | **After the device-registration branch merges** | Adding to the current branch; deferring Tasks 13-14 |
