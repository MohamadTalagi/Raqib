# ERR-007 — `mqtt-broker-secure` exits (code 13) — non-root mosquitto user can't read the 600-permission broker key

- **Date:** 2026-07-08
- **Component:** lab/certs, lab/mqtt/secure
- **Severity:** medium
- **Status:** resolved
- **Author:** Claude (subagent-driven-development, Task 16 controller-side integration verification)

## What happened
After wiring `mqtt-broker-secure` into `docker-compose.yml` (Task 16) and bringing the full lab up,
the container exited immediately with code 13 (`EACCES`), retried once, and exited again — with no
explicit error line in `docker logs`, just `Info: running mosquitto as user: mosquitto.` printed
twice.

## Exact error / symptom
```
1783467262: Info: running mosquitto as user: mosquitto.
1783467277: Info: running mosquitto as user: mosquitto.
```
(exit code 13, container state `Exited (13)`)

## Environment
- OS / shell: `eclipse-mosquitto:2` official image
- Tool + version: Mosquitto broker, drops privileges from root to a `mosquitto` user at startup
- Relevant files: `lab/certs/generate.sh` (generates `mqtt-server.key`), `lab/mqtt/secure/mosquitto.conf`

## Root cause
`openssl genrsa` creates key files with mode `600` (owner-read-only), owned by `root` (the user the
`cert-init` container ran as). `eclipse-mosquitto:2` starts as root but immediately drops privileges
to a dedicated non-root `mosquitto` user before reading its configured `keyfile` — which then can't
read a `root`-only-readable file on the bind-mounted `/certs` volume, causing exit code 13
(permission denied) at startup, before it prints anything more specific to the log.

## The fix
`lab/certs/generate.sh` now `chmod 644`s `mqtt-server.key` specifically, right after all certs are
generated:
```sh
chmod 644 "$OUT/mqtt-server.key"
```
`weak.key` and `strong.key` are left at the default `600` — their consumers (the smart-camera
containers) run as root (no `USER` directive in that Dockerfile), so they can read `600` files fine
and there's no reason to loosen them.

## How to prevent it next time
When a container mounts a private key generated by a *different* container, check which user each
side runs as. A `600`-permission key generated by one root process is invisible to a different
container's non-root runtime user, even on the same bind mount — the fix belongs at generation time
(permissions matching the actual consumer), not by making the consuming service run as root (which
would undo an intentional least-privilege default in the upstream image).
